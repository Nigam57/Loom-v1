# Loom Master Plan — Enhance Every CLI, Redesign the Workbench

> **For Claude:** This is the roadmap. Each phase gets its own bite-sized plan via superpowers:writing-plans (brainstorming first when the design is open). Plans 01 and 02 are already written in full; execute them with superpowers:executing-plans or superpowers:subagent-driven-development. Work each plan in its own git worktree/branch.

**Goal:** Make every connected CLI agent (Antigravity, Claude Code, Gemini, Codex, OpenCode, any CLI) work better and work *together*, by giving all of them the same shared tools — rooms, delegation, memory, skills, web, GitHub, approvals — through one Loom tool hub, and present it in a workbench UI with real taste.

**Direction (owner decision, 2026-09-23):** Loom is the *arena*, not another agent. It does **not** run its own LLM loop (vision principle: "Loom wraps and enhances the CLIs and does not reimplement their agent loops"). "Hermes-agent level" means capability parity (memory, learning from experience via skills, scheduling, delegation, messaging triggers) delivered **to** the CLIs through structured adapters and MCP.

**Source of truth for scope:** `D:\Loom\legacy v1\docs\01-Vision\vision.md` (capability map: Run, Coordinate, Remember, Extend, Automate, Observe & control, Secure, Workspace UX). The legacy decision records (ADRs) still apply unless a phase below says otherwise. ADR-002 (Headless JSON > ACP > PTY) is the basis of Phase 1.

## Where we are (2026-09-23 analysis)

**Backend.** Chat talks to CLIs by typing into a hidden PTY and **scraping the screen**. After roughly 4 s of silence (a 3 s window plus a 1 s debounce), `terminal_engine/filters` guesses the reply from `❯`/`•` glyphs. The Antigravity profile (`filters/profiles/antigravity.rs`) passes the **whole screen** through, which is why the TUI chrome shows up in chat. `chat_dispatch_batcher.rs` locks each member's queue until that guess succeeds, so login and setup prompts deadlock (a 30 s force-flush is the only escape). Other gaps:
- No tool-call, usage or cost data.
- Delivery has TODOs where retries and a dead-letter queue should be (`pipeline/reliability.rs`).
- Skills and plugins are UI stubs.
- Agent onboarding is a single line.
- There are zero Rust tests.

**Verified on this machine:**
- `agy` 1.2.9 produces clean `stream-json` headless output: text deltas, tool calls with parameters, per-step usage, and a final result.
- `claude` 2.1.280, `gemini` 0.49.0 and `opencode` 1.18.31 are installed.
- `agy` supports `--conversation`, `--mode accept-edits|plan`, `--sandbox`, `mcp add` and `plugin`.

**UI.** It still reads as the Golutra chat app it was forked from:
- Friends, channels, owner/admin roles and "Billing access" copy.
- Glassmorphism with neon glow.
- Be Vietnam Pro for everything, a sky-blue accent, and 460 arbitrary sizes.
- Light mode held together by `!important` overrides.
- Agent output rendered as plain text, with no tool-call view.
- Terminals open in a separate window from the rooms.
- No command palette.
- Dead controls, which break the vision's "nothing unbuilt is faked" principle.

**Repo.** `Loom v1/` is its own git repository (branch `master`; remotes `loom_v1` → `github.com/Nigam57/Loom-v1` and `origin` → upstream Golutra). The outer `D:\Loom` repo holds only the legacy prototype. The licence is left as it is (owner: no preference).

## Phases and plans

Plans that already exist are marked ✅. The rest are scoped here and expanded with writing-plans when started.

### Phase 0: Safety net (before any code)
- Commit a baseline (see Plan 01 Task 0). Add CI: `cargo test --lib`, `pnpm lint`, `pnpm test`, `pnpm build`.
- **Owner decision:** licence. Check Golutra's licence terms, then choose between AGPL v3 (the vision) and BSL 1.1 (the README) and fix `README.md`, `LICENSE` and `Cargo.toml`.
- Remove the committed artefacts `graphify-out/`, `.tmp-xterm/`, `output.txt`, `patch.py`, `rewrite.py` and `ter` from the product tree (or add them to `.gitignore`).

### Phase 1: Structured adapters, which fixes chat. ✅ `2026-09-23-01-structured-agent-adapters.md`
- Run `agy` and `claude` headless with `stream-json` and map their output to one `AgentEvent` type. Reuse the chat pipeline; each member gets its own turn queue, CLI sessions are kept per room, errors are posted to chat, and `agent_stop` works as a kill switch. Remove the Antigravity passthrough.
- **1b (next plan):**
  - Adapters for Gemini (`--output-format stream-json`), Codex (`codex exec --json`, not installed yet) and OpenCode (`opencode run --format json`). Capture real fixtures first.
  - Resolve npm `.ps1`/`.cmd` shims to real executables.
  - Persistent processes via `--input-format stream-json` (agy and claude), with prompts on stdin.
  - Windows Job Objects for process-tree control (port from `legacy v1/loom-desktop/src-tauri`).
  - Default to `agy --mode accept-edits` instead of `--dangerously-skip-permissions` when "unlimited" is off.
  - An ACP adapter where a CLI supports it (Hermes, per the legacy research).

### Phase 2: Loom Tool Hub, one MCP server for every CLI
This is the core of "make all CLIs work together with all the tools."
- **`loom-mcp`**: a new stdio MCP binary next to `loom-cli`/`shim` in `src-tauri/src/bin/`. It forwards tool calls to the running app over the existing named pipe (`runtime/command_ipc.rs`, `\\.\pipe\loom-command`), so there's one process model and no network port.
- **Tools, in delivery order:**
  1. **Rooms:** `room_post_message`, `room_read_messages` (the legacy `spec-conversation.md` design).
  2. **Delegation:** `ask_agent(member, prompt)`. One CLI can hand work to another; the call runs through the Phase 1 runtime and returns the other agent's final answer.
  3. **Approvals:** `approval_request`. Claude uses it through `--permission-prompt-tool`; for other CLIs it's a Loom-side gate. Requests land in the approval inbox (Phase 7).
  4. **Workspace context:** `workspace_summary`, `workspace_search` (ripgrep-backed).
  5. **Web:** `web_fetch`, `web_scrape` (the vision's built-in Scrapling tool, run as a managed sidecar).
  6. **GitHub:** `github_*` through the one-click connector (legacy ADR-005, device flow). Agents never hold long-lived tokens.
  7. Memory and skills tools (Phases 3 and 4).
- **Injecting the tools into each CLI:**
  - claude: `--mcp-config <generated.json>` on every headless turn, so the user's global config isn't touched.
  - agy: `agy mcp add` (global). Consent is required once, and it can be undone from Settings.
  - gemini: `mcpServers` in `.gemini/settings.json` (workspace scope).
  - opencode: its config file.
  - Check each mechanism against the installed version before writing code, as was done for agy.
- **Guards:** a per-room allowlist of tools, a turn and time budget on `ask_agent` (no infinite agent ping-pong), and every call written to the audit log.
- **Acceptance:** in a room with an Antigravity agent and a Claude agent, you ask Claude to "have Antigravity review this diff." Claude calls `ask_agent`, Antigravity's review shows up in the room, and Claude continues.

### Phase 3: Shared memory (the vision's Remember area; legacy ADR-007)
- The source of truth is a markdown vault in `<workspace>/.loom/memory/` (Obsidian-compatible, links and graph). An index in SQLite FTS5 plus sqlite-vec provides hybrid search.
  - The app currently uses `redb` for chat. Adding `rusqlite` for the index is a new dependency and needs a short decision record.
- MCP tools: `memory_search`, `memory_read`, `memory_write`, `memory_link`.
- **Session recall:** every turn's `AgentEvent`s are already structured (Phase 1), so full-text search over past sessions is indexing work, not scraping.
- **The Hermes-style learning loop:** after a room goes idle, Loom asks one designated headless agent to write a dated summary note (decisions, facts, open threads). This uses the CLI's own loop, so it isn't a Loom agent loop. The user can review and edit the note.

### Phase 4: Skills and extensions (Extend)
- **A write-once skills library** in the `SKILL.md` standard, stored in `.loom/skills/` (replacing today's symlink stub). Loom syncs it to each CLI's native location: `.claude/skills/`, agy plugins/skills, and `AGENTS.md`/`GEMINI.md` includes. It's also available on demand through the MCP tools `skill_list` and `skill_get`.
- **Improving skills:** a `skill_propose(name, diff)` tool lets an agent suggest a new or improved skill after it solves something. Proposals wait for approval in the inbox (Phase 7), so skills get better through experience without anything self-modifying silently.
- **Install anything from GitHub:** the legacy ADR-012 classifier sorts a repo into MCP server / tool / skill / agent-config / plugin, then installs it once and exposes it to every CLI through Phase 2. Isolation for installed code follows ADR-006.
- Replace the fake Skill Store and Plugin Marketplace with one honest "Extensions" list. Anything unbuilt is labelled "not implemented yet".

### Phase 5: Coordination (Coordinate)
- Port the Conversation Rooms router and guards from the legacy prototype (`legacy v1/loom-desktop/src-tauri/src/router/`): max turns, timeout, spend cap, an n-gram loop detector, human approval of turns, and a `writer` role (only the writer agent can edit files).
- A git worktree per agent (`.worktrees/<member>`) and **Arena Mode**: the same task goes to several CLIs, then you compare diffs side by side and merge.
- A flow view of who is doing what (driven by `agent-event`).

### Phase 6: Automation (Automate; legacy ADR-008)
- A scheduler (cron), webhook, git-push and Telegram triggers, each bound to a room plus a prompt template, with approval gates for unattended runs. Results post to the room and optionally to a messaging channel.
- Start with a list-based rule editor; the node-graph editor comes later.

### Phase 7: Observe and control
- A usage and cost ledger built from `AgentUsage` (tokens always; USD where the CLI reports it, which Claude does and agy doesn't). Budgets per room and per member, enforced before each turn is dispatched.
- **An approval inbox** for tool permissions, skill proposals and unattended-run gates.
- A global kill switch (`agent_stop` for every member), an audit log (every tool call, turn and approval), and live traces.

### Phase U1: Design system foundation. ✅ `2026-09-23-02-design-system-foundation.md`
- Geist + Geist Mono.
- An OKLCH neutral ramp (hue 255) with one "thread amber" accent (`oklch(0.80 0.13 70)` dark, `oklch(0.60 0.14 60)` light). This is a proposal: change it in one place (`global.css`) if you want a different accent.
- A 4-step radius scale, a named type scale, motion tokens with reduced-motion support, and a z-index scale.
- A tested codemod that replaces hardcoded values with tokens; delete the `!important` light-mode block.
- Remove glass, glow and gradients. Add visible focus rings and an xterm theme driven by the tokens.

### Phase U2: Workbench layout and information architecture (Hallmark: "match the nav to the genre", here an IDE)
- **Activity bar**, 40px, with a 2px accent marker: Rooms, Agents, Extensions, Memory, Settings.
- **Explorer**, resizable: a tree of rooms, agents with live status (running / waiting for input / idle / error, plus elapsed time), and the workspace.
- **Editor area:** rooms *and* PTY panes as tabs in the **same window**, splittable. This ends the separate terminal window; `App.vue:80,195` routing changes.
- **Inspector**, a right-hand slide-over: agent details (type, model, cwd, session), tool calls, context and diffs.
- **Status bar**, 24px: path, git branch, running agents, and tokens/cost in tabular numbers.
- **Command palette** on Ctrl+K: add agent, new room, run skill, stop agent, switch theme. It replaces most of the 9 modals; renaming becomes inline.
- **Remove what's left of Golutra:** the friends view, owner/admin/billing roles, the "Spotify Player" string, the emoji picker and quick-prompt pills. Slash commands and `@file` context take their place in the input.

### Phase U3: Agent messages that show the work
- Markdown with syntax highlighting (`markdown-it` plus `shiki`), rendered in a web worker for long replies.
- Each agent message gets a mono header (`claude-code · opus · 00:42 · running`), a body, and collapsible tool-call rows fed by the `agent-event` stream (name, key parameter, duration, errors). Rows are separated with `divide-y`, not bubbles.
- Stop and retry controls. A usage chip on the final message.
- A "waiting for input" state with a button to open the agent's PTY, the honest way to handle interactive login and setup.

### Phase U4: Finish
- Loading skeletons, empty states and inline errors on every screen (the audit's missing-states table).
- Copy: sentence case, no Title Case, and hardcoded strings moved into i18n.
- Icons: Material Symbols → Phosphor, one stroke weight.
- Split `Settings.vue` (2,243 lines) into section components.
- The pre-flight checklist from Plan 02, Task 9, rerun across the new layout.

1. `brainstorming`: settle the open design questions for the phase (skip it for Plans 01 and 02; they're decided).
2. `writing-plans`: write the bite-sized plan into this folder, `2026-MM-DD-NN-<phase>.md`.
3. `executing-plans` in a separate session, or `subagent-driven-development` in this one: one task at a time, TDD, a commit per task, review between tasks.
4. For UI phases, also apply `redesign-existing-projects` (audit → fix, no rewrites) and finish with the pre-flight checklist from Plan 02, Task 9.
